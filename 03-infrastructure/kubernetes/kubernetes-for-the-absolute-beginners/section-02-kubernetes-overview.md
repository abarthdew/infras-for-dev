# 4. Containers Overview
## Kubernetes or K8s
- 쿠버네티스는 구글에서 기본적으로 개발되고, K8s라는 이름으로도 알려짐.
- 가장 인기있는 컨테이너 조정 기술.
## Container + Orchestration
### 🔰Docker란?
![]()
- 서로 다른 어플리케이션을 개발할 때 발생하는 문제
	1. 내부 운영체제의 호환성
	2. 서비스의 라이브러리나 의존성의 호환을 체크해야 함
	3. 때문에, 각 요소의 새로운 버전을 업데이트 하거나 데이터베이스를 변경해야 함
	4. 이렇게 되면 호환성 문제가 생길 수 있음
![]()
- 호환성 문제를 해결하기 위해 제시된 방법이 바로 도커를 사용하는 것
![]()
- 도커를 사용하면 각각의 컨테이너로 분리된 요소를 호환성 문제 없이, 간단한 도커 명령어로 구동할 수 있게 됨
![]()
### 🔰Container란?
- 컨테이너 : 완전히 고립된 환경. 가상 머신처럼, 자신만의 서비스 프로세스가 있고, 네트워크 인터페이스 등이 구축되어 있음.
- 각 컨테이너들이 같은 OS Kernel을 공유하고 있다는 것만 빼면!
![]()
- 컨테이너는 원래 있는 개념이었음. low level 환경의 컨테이너들을 도커를 사용함으로써 high level화 시켜 사용성을 증대시킴.
### 🔰 도커를 이해하기 위해 : OS 시스템의 개념에 대하여
- 우분투, 센토스 등 모든 OS는 (1) OS Kernel과 (2) 소프트웨어 세트로 이루어짐.
	1. OS Kernel : 하드웨어 자원 상호작용, 관리, 프로세스 제어
	2. 소프트웨어 : 드라이버, 컴파일러, 파일 관리자, 개발자 도구 등 서로 다른 유저 인터페이스를 구성함
	⇒ OS Kernel이 operating system을 가로지르며 각기 다른 OS의 소프트웨어를 공유하게 함.
![]()
### 🔰 Sharing the Kernel
- 기본적으로 동일한 커널 위에서 동작하는 한, 도커는 어떤 OS 환경에서도 운영될 수 있음.
- 예시) 리눅스 : 데비안, 센토스, 우분투 등.
![]()
<callout icon="💡" color="gray_bg">
	윈도우는 안 됨 : docker host가 Linux OS에서 구동되기 때문에, 윈도우는 Window server가 필요함.
</callout>
- 하이퍼바이저 도커는 다른 작업을 가상화하고 실행하는 것이 아님 ⇒ 시스템과 커널이 동일한 하드웨어에 있음
- 도커의 주된 목적은 컨테이너화된 애플리케이션을 옮기고 실행하는 것
### 🔰 가상 머신과 컨테이너 차이
- 각각의 가상 머신은 내부에 자체 OS를 가지고 있음.
- 도커는 컨테이너에서 자원을 공유하는 것으로 고립성이 덜함.
![]()
### 🔰 How is it done?
- 도커에 서비스를 올릴 때, 더 많은 서비스가 필요할 경우(ex. NodeJS) 인스턴스를 쌓으면 됨.
- 로드 발런싱을 설정하면, 인스턴스가 내려갔을 때 해당 인스턴스를 종료하고 새 인스턴스가 올라감.
![]()
## Container & Image
### 🔰 Image
- 가상 환경에서 작업할 package 혹은 template
### 🔰 Container
- 고립되고, 특정 환경으로 구축되고, 과정의 집합인 이미지의 실행 인스턴스
![]()
### 🔰 Container Advantage
![]()
1. 전통적으로, 개발자는 개발을 한 후,
2. production 환경에서의 배포와 관리를 위해 상부에 어플리케이션을 전달.
3. 호스트가 어떻게 세팅되어야 하는지, 무엇이 필수적으로 설치되어야 하는지, 어떤 의존성이 설정되어 있는지 등 정보에 대한 설명서를 제공함.
4. ops 팀은 이 가이드를 이용해 에플리케이션을 세팅함. ops 팀이 자기만의 어플리케이션을 개발하지 않으면, 설치하는 데 문제가 생김.
5. 이러한 문제로, 인프라 환경은 도커 파일 형태로 개발자들이 관리하게 됨.
![]()
6.  도커 파일로 어플리케이션 이미지를 생성하는 방식으로 더 쉽게 사용 가능.
![]()
7. 해당 이미지는 어떤 컨테이너 플랫폼에서도 구동 가능하며 어디서든 사용 가능함.
8. 그러므로, ops 팀은 간단히 이미지만 사용해서 어플리케이션을 배포하면 됨.
9. 이미지는 개발자들이 개발한 후에 작동되는 것이므로 작업이 변경되지 않고, production에서 배포될 때 계속해서 동일한 방식으로 동작함.
# 5. Container Orchestration
- 도커 컨테이너에 어플리케이션 패키지를 담을 수 있음.
![]()
- 다음은?
	1. 어떻게 생산물을 구동하고,
	2. 어플리케이션은 데이터베이스나 메세지 서비스 또는 백앤드 서비스 같은 다른 컨테이너와 어떻게 의존하며,
	3. 유저의 수가 늘어나거나 어플리케이션 확장이 필요할 때는 어떻게 하는가?
	4. 로드가 줄어들 때 축소는 어떻게 하는가?
![]()
- 자원이 세팅되거나 가용한 기반 플랫폼이 필요함.
- 이 플랫폼은 컨테이너들 간 연결성과 자동 확장이나 축소가 가능한 조정이 필요함.
- ⇒ 모든 컨테이너 자동 배치와 관리 과정이 Container Orchestration이라고 불림.
![여러가지 컨테이너 조정 기술 프로그램]()
- 쿠버네티스는 컨테이너 조정 기술임.
- 쿠버네티스는 GCP, Azure, AWS 와 같은 클라우드 서비스를 제공함.
![]()
- 쿠버네티스를 사용하면 하드웨어 문제로 인한 어플리케이션 다운에 대한 가용성이 높아짐.
- ⇒ 서로 다른 노드에 여러 개의 어플리케이션 인스턴스가 작동되고 있기 때문.
![]()
- 사용자 요청은 여러 개의 컨테이터를 통해 로드 밸런싱됨.
- 요청이 많아질 때, 더 많은 어플리케이션 인스턴스를 매끄럽고 빠르게 배치함.
- 하드웨어 자원이 초과했을 때 서비스 수준에서 작업을 수행할 수 있음.
![]()
- 어플리케이션 중지 없이 기반 노드를 확장하거나 축소할 수 있음.
- 이 모든 것을 명시적인 객체 구성 파일로 쉽게 구성할 수 있음.
<callout icon="💡" color="gray_bg">
	**결론 : 쿠버네티스는 컨테이너 조정 기술이며, 2개 이상의 노드가 존재하는 환경에서 많은 수의 배치와 관리를 조장하는 데 쓰임.**
</callout>
# 6. Kubernetes Architecture
## Node
### 🔰 노드란?
![]()
- A Machine, 쿠버네티스가 설치된 물리적 혹은 가상의 머신.
- 노드란 worker machine을 뜻함.
- 컨테이너들이 쿠버네티스에 의해 생성되어 있음.
- 과거에는 minions라고도 불림.
![]()

- 그래서 여러 개의 노드가 필요함.
- 로드 밸런싱에도 유용.
![]()
## Cluster
1. 누가 클러스터 관리 책임이 있는가? 클러스터 저장소에 대한 정보는 어디에?
2. 노드는 어떻게 모니터링 되는가?
3. 노드가 중지되었을 경우 workload는 어떤 worker node로 옮겨가는가?
4. ⇒ Master Node가 필요한 이유
![]()
- 마스터 노드는 쿠버네티스가 설치된 또 다른 노드며, 마스터로서 기능함.
![]()
- 마스터는 클러스터 내 노드를 감시하고 워커 노드 컨테이너의 실제 조정에 대한 책임을 가짐.
![]()
- 쿠버네티스를 설치하면 따르는 요소들 :
	1. `API Server` : 프론트엔드로 동작, 유저와 management devices, cli, 모두 쿠버네티스 클러스터 API Server를 통해 소통.
	2. `ETCD` : ETCD Key store. ETCD는 분배된 신뢰할 수 있는 키-밸류 저장소. 쿠버네티스에선 모든 클러스터에서 관리되는 데이터를 저장하는 용도로 쓰임.
	3. `Scheduler` : 다수의 노드 사이에서 작업이나 컨테이너 분배를 담당. 새롭게 생성된 컨테이너를 주시하고, 그들에게 노드를 할당함.
	4. `Controller` : 조정의 수뇌부. 노드, 컨테이너, 엔드 포인트가 다운됐을 때 알림과 반응을 하는 역할. 이 경우, 새로운 컨테이너를 만들 것인지 결정함.
	5. `Container Runtime` : 컨테이너가 구동될 때 보통 기반이 되는 소프트웨어. 이 경우 Docker라고 할 수 있음. (다른 옵션도 있음)
	6. `Kublet Service` : 클러스터 내에서 각각의 노드를 실행시키는 에이전트. 컨테이너가 예상대로 노드에서 동작하고 있는지 확인하는 역할.
<callout icon="💡" color="gray_bg">
	**ETCD**<br>다수의 노드와 다수의 마스터가 클러스터를 이루고 있을 때, ETCD Store는 분배된 클러스터 내 모든 노드의 정보를 저장함. ETCD는 마스터 사이에서 충돌이 일어나지 않도록 보장하기 위해 클러스터 내 구현된 잠금을 관리함.
</callout>
### 🔰 어떻게 이 요소들이 두 가지 유형의 서버(Master, Worker)에 분배될 수 있을까?
- 다른 말로, 어떻게 하나의 서버가 마스터가 되고, 다른 하나가 워커가 되는가?
- 워커 노드 또는 minion은 컨테이너가 호스트되는 곳임.
<callout icon="💡" color="gray_bg">
	**예시) 도커 컨테이너**<br>Docker Container를 시스템에서 실행하기 위해선 컨테이너 런타임이 설치되어 있어야 하고, 거기서 컨테이너 런타임이 떨어짐. 이 경우 Docker에서 발생되는 일임. 꼭 도커로 할 필요는 없고, Rocket이나 Cryo 같은 다른 컨테이너 런타임 대안이 가능함.<br>**해당 강의에서는 컨테이너 런타임 엔진으로 Docker를 사용함.**
</callout>
### 🔰 어떤 요소가 마스터와 워커 노드로 구성되는가?
- : 인프라 환경울 구성할 때, 다른 시스템 위에 올바른 요소를 설치하고 설정하는 데 도움이 되기 위하여.
![]()
- 마스터 서버는 <span color="red">`kube API Server`</span>를 가지고 있으며, 이것이 마스터가 되기 위한 필요조건임.
- 유사하게, 워커노드도 <span color="red">`kublet 에이전트`</span>를 가지며, 마스터와 상호작용하는 일을 담당함. 워커 노드에게 유익한 정보를 제공하며, 워커 노드 위에서 마스터가 요청한 동작을 전달함.
- 모든 정보는 마스터 저장소에 키-밸류 형태로 모임. 키-밸류 저장소는 <span color="blue">`ETCD 프레임워크`</span>를 기반으로 하고 있음. (현재 강의에서)
- 마스터는 <span color="green">`Control Manager`</span>와 <span color="purple">`스케줄러`</span>도 가지고 있음.
## Kubectl
- kube command line tool / kubectl / kube control
- kubectl tool은 쿠버네티스 클러스터에 어플리케이션을 배치, 관리할 때 사용함.
- 클러스터 정보를 검색할 때, 클러스터 내 다른 노드의 상태를 검색할 때, 다른 많은 것들을 관리할 때 사용.
### 🔰 명령어
![]()
```bash
kubectl run hello-minikube // 클러스터에 어플리케이션 배치할 때 사용
kubectl cluster-info // 클러스터에 대한 정보를 검색할 때 사용
kubectl get nodes // 클러스터의 노드 부분에 대한 리스트를 검색
```
