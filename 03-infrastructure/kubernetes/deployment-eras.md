## 전통적인 배포 시대

- 초기 조직은 애플리케이션을 물리 서버에 직접 실행함.
- 한 물리 서버에서 여러 애플리케이션의 리소스 한계를 정의할 방법이 없어 자원 할당 문제가 발생.
- 리소스 전부를 차지하는 애플리케이션 인스턴스가 있으면 다른 애플리케이션 성능이 저하됨.
- 해결책으로 애플리케이션마다 별도의 물리 서버를 쓰면, 리소스가 충분히 활용되지 못하고 서버 유지 비용이 커짐.

## 가상화된 배포 시대

- 단일 물리 서버의 CPU에서 여러 가상 머신(VM)을 실행할 수 있게 함.
- VM 간 애플리케이션을 격리해 일정 수준의 보안성 제공.
- 물리 서버 리소스를 더 효율적으로 활용, 애플리케이션 추가/업데이트가 쉬워짐.
- 각 VM은 가상화된 하드웨어 위에서 자체 운영체제를 포함한 모든 구성 요소를 실행하는 완전한 머신.

## 컨테이너 배포 시대

- 컨테이너는 VM과 유사하지만 격리 속성을 완화해 애플리케이션 간 운영체제(OS)를 공유 → 더 가벼움.
- VM처럼 자체 파일 시스템, CPU 점유율, 메모리, 프로세스 공간을 가짐.
- 기본 인프라와의 종속성이 끊어져 있어 클라우드나 OS 배포본 어디에나 이식 가능.

## 컨테이너가 제공하는 추가적인 혜택

- **기민한 애플리케이션 생성과 배포**: VM 이미지보다 컨테이너 이미지 생성이 쉽고 효율적.
- **지속적인 개발/통합/배포**: 이미지 불변성 덕분에 안정적으로 빌드·배포·롤백 가능.
- **개발과 운영의 관심사 분리**: 빌드/릴리스 시점에 이미지가 만들어지므로 애플리케이션이 인프라에서 분리됨.
- **개발/테스트/운영 환경 간 일관성**: 로컬에서도 클라우드와 동일하게 동작.
- **클라우드 및 OS 배포판 간 이식성**: Ubuntu, RHEL, 온프레미스, 주요 퍼블릭 클라우드 어디서든 구동.
- **애플리케이션 중심 관리**: 가상 하드웨어 위에서 OS를 실행하는 수준에서, 논리적 리소스를 사용하는 OS 위에서 애플리케이션을 실행하는 수준으로 추상화 수준이 높아짐.
- **느슨하게 결합된 분산 마이크로서비스**: 모놀리식 스택 대신 작고 독립적인 단위로 쪼개져 동적으로 배포·관리 가능.
- **리소스 격리**로 애플리케이션 성능 예측 가능, **자원 사용량** 측면에서 고효율·고집적.

## Kubernetes가 왜 필요한가

- 컨테이너는 애플리케이션을 포장·실행하는 좋은 방법이지만, 프로덕션에서는 컨테이너가 다운되지 않도록 관리해야 함.
- 예를 들어 컨테이너가 죽으면 다른 컨테이너를 다시 시작해야 하는데, 이를 시스템이 자동으로 처리해주는 것이 Kubernetes가 필요한 이유.
- Kubernetes는 분산 시스템을 탄력적으로 실행하기 위한 프레임워크를 제공하고, 애플리케이션의 확장·장애 조치·배포 패턴(카나리아 배포 등)을 지원함.

## Kubernetes가 제공하는 항목들

- **서비스 디스커버리와 로드 밸런싱**: DNS 이름이나 자체 IP로 컨테이너를 노출. 트래픽이 많으면 네트워크 트래픽을 로드밸런싱.
- **스토리지 오케스트레이션**: 로컬 저장소, 퍼블릭 클라우드 저장소 등 원하는 저장소 시스템을 자동 탑재.
- **자동화된 롤아웃과 롤백**: 배포된 컨테이너의 원하는 상태를 서술하고, 실제 상태를 원하는 속도로 원하는 상태로 변경.
- **자동화된 빈 패킹**: 각 컨테이너가 필요로 하는 CPU/메모리를 지시하면, 클러스터 노드에 맞춰 배치해 리소스를 가장 잘 사용하도록 함.
- **자동화된 복구(Self-healing)**: 실패한 컨테이너를 재시작/교체하고, 사용자 정의 상태 검사에 응답하지 않는 컨테이너를 죽이며, 준비가 끝날 때까지 클라이언트에 노출하지 않음.
- **시크릿과 구성 관리**: 암호, OAuth 토큰, SSH 키 등을 이미지 재구성 없이 저장·관리·배포·업데이트.

## Kubernetes가 아닌 것

- 전통적인 올인원 PaaS가 아님 — 하드웨어 수준보다는 컨테이너 수준에서 운영하며 모놀리식이 아님.
- 소스 코드를 배포하거나 애플리케이션을 빌드하지 않음(CI/CD는 별도 영역).
- 미들웨어, 데이터 처리 프레임워크, 데이터베이스, 캐시 같은 애플리케이션 레벨 서비스를 직접 제공하지 않음 — 다만 이런 컴포넌트들이 Kubernetes 위에서 구동될 수는 있음.
- 로깅/모니터링/경보 솔루션을 포함하지 않음 — 메트릭을 수집·노출하는 메커니즘만 제공(자세한 내용은 [로깅과 모니터링](./logging-and-monitoring.md) 참고).
- 설정 언어나 시스템을 강제하지 않고, 선언적 API를 제공.
- 단순 오케스트레이션 시스템이 아니라, 독립적이고 조합 가능한 제어 프로세스들로 구성되어 현재 상태를 지속적으로 원하는 상태로 수렴시키는 시스템 — 중앙화된 제어 없이도 확장 가능하고 회복력을 갖춤.
